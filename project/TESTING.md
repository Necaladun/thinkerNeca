## BAL-003 Titanium Unity pod mineral-resource reroll — initial Windows positive, 7 November 2026

**Confirmed source loophole:** `goody_box()` can award a resource by setting `BIT_BONUS_RES` **after** new-map geological placement has finished. That award is resolved by `bonus_at(x,y)` using explicit bias flags and coordinate/seed-derived classification. The geological placement rule cannot prevent a later mineral-resource discovery on an already-present Titanium tile.

**Approved source fix on PR #4:** after the pod first sets `BIT_BONUS_RES` and determines its proposed resource, **only** `RES_MINERAL` on **independent** `MINOR_TITANIUM` is converted to 50/50 nutrient or energy via `goody_rand(2)`. Clear the three resource-type bias flags, then set `BIT_NUTRIENT_RES` for either replacement, adding `BIT_ENERGY_RES` only for energy. This specific combination is required by the existing `underlying_resource_bonus_at()`: `BIT_NUTRIENT_RES` forces the explicit selection path regardless of coordinate-derived `ret`, and that path returns energy when `BIT_ENERGY_RES` is also set, otherwise nutrient. Requery `bonus_at()` before reporting/redrawing. This does not affect Uranium+energy, a pod's non-mineral outcomes, regular natural resources, editor bonuses or existing save data. It uses an additional RNG draw **only** for that targeted mineral-on-Titanium pod case.

**Windows Develop user report:** on a spawned Unity pod at independent Titanium **(12,58)**, repeated resource-award attempts produced **nutrients** and later **energy**, both allowed conversion results. The user originally tested (13,59) and got nutrients; that location's expected coordinate resource is also nutrients, so it did not isolate the reroll. At (12,58), the underlying coordinate-derived resource would be **minerals** as previously evaluated for the supplied Zakharov 2101 save, so the two observed non-mineral awards are positive evidence that the pod conversion runs in-game. No mineral reward was reported on that tile. This is **user-observed functional smoke coverage**, not a statistically established 50/50 rate or proof that all coordinates cannot produce minerals. The live code and source contract account for the expected coordinate overrides. **Still open elsewhere:** explicit same-build save/reload of the awarded resource, fresh-map Titanium/non-mineral overlap and broader Mine balance. Subsequent Forest, fungus-clearing and Mine yield observations are recorded in the BAL-003 section below. There is no need for further repetitive pod save-scumming to establish the central behaviour.

## BAL-003 geology-versus-Forest and resource exclusions — targeted Windows pass, 7 November 2026

**New source behaviour on PR #4:** actual `mod_mine_yield()` suppresses independent Titanium minerals on a `BIT_FOREST` tile, actual `mod_energy_yield()` suppresses independent Uranium energy on that tile, and the AI `item_yield(..., BIT_FOREST)` forecast suppresses both while retaining any Jungle nutrient contribution. Stored independent features are never deleted when building/removing Forests; after removal, their bonuses can contribute again. The standard Forest N/M/E baseline and normal resource bonuses are unchanged.

**New-world generation:** a candidate for Titanium is rejected when `mod_bonus_at(tx,ty)==RES_MINERAL`, covering explicit `BIT_BONUS_RES` and procedural map-seed resources. Uranium and Titanium+nutrient/energy resource candidates remain eligible. There is no automatic relocation/deletion of an ordinary mineral bonus, and existing saves are not rewritten. The Mine's current single extra modifier when Titanium is present is deliberately unchanged for the 3–5-tile distribution trial.

**Windows Develop user report (7 November):** Forest on independent Titanium suppressed its geological +1 mineral, and removing that Forest restored the bonus. Forest on independent Uranium suppressed its geological +1 energy and removing the Forest restored that bonus. Mine + Road on Titanium produced **4 minerals on Rolling** and **3 on Flat**; these are observed values with the retained Titanium Mine modifier, not a settled balance endorsement. Clearing fungus over geology behaved correctly (the underlying geological bonus became available). The user also reports that save → quit → reload → turn advance worked normally on this tested build, and that fungus extraction behaved normally. The user further reports inspecting fresh maps: no normal mineral-resource tiles were found on Titanium; ordinary nutrient- and energy-resource overlaps were present, and normal mineral-resource deposits were frequently adjacent to Titanium. Adjacency is an observation, not a new exclusion/spacing rule. These are targeted user-observed functional smoke checks, not an automated regression or an exhaustive seed-by-seed survey; no exact DLL commit was supplied for this follow-up.

**Still outstanding:** a quantitative multiple-seed/map-size generation survey; ordinary Forest/Jungle/resource yield comparisons and exact per-tile post-reload snapshots on the final integrated build. Overall persistence, Forest suppression/restoration on both geology types, fungus extraction, Mine output and sampled fresh-map resource-exclusion smoke tests pass by user report. AI's projected Forest yield remains source/CI checked only. Dedicated constructed minor stacks, Release/PRACX parity and missing-art/editor compatibility are separately deferred, not implicitly passed.

**AI Former limitation (source audit, no Windows AI acceptance):** `src/move.cpp::can_mine()` unconditionally rejects non-rocky *land* squares (`!sea && !sq->is_rocky()`), even when independent Titanium is present and a Mine + Road is productive (observed 4M Rolling, 3M Flat). A second predicate rejects any tile without a normal mineral resource when `mod_mine_yield()` is already at least **2** and the faction lacks the 3-mineral technology unlock, despite the experimental `tile_output_limit=3,3,3`; this can exclude Titanium tiles even after the rockiness restriction is addressed. `select_item()` uses this predicate for standard `FM_Auto_Full`, considers Forest and Solar candidates before the Mine branch, and `former_tile_score()` does not explicitly prioritise independent Titanium. The player-controlled `FM_Mine_Road` special mode can directly request a Mine without calling `can_mine()`; this is not evidence the ordinary AI will do so. See AI-002; no former source change or runtime AI test was made.

## TERR-002 geology distribution change — new Windows validation pending, 7 November 2026

**Source change proposed/implemented on PR #4 after REND-001 acceptance:** geological patch target sizes now weighted `{3,4,4,4,5}` (mean four instead of six), per-type attempt targets are old 2–6 formula multiplied by 1.5 and rounded to nearest integer (3–9). The generator no longer clears `BIT_FUNGUS` when committing a geology patch, but keeps the original eligibility, two-tile buffer, retries, alternation, separate type RNG seeds, per-tile codes and full-patch-only commitment. A candidate patch that does not reach its target is discarded before any tile is marked. The live yield code applies fungus-specific values until fungus is removed, so a fungus-covered geology deposit is a later exploitation opportunity rather than an immediate +1 production tile.

**Test required after CI:** generate fresh worlds with different seeds and at least two map sizes; count realised Uranium and Titanium deposits and covered tiles (expected roughly stable coverage if placement succeeds), verify no independent-type/major-landmark overlap, confirm pre-existing fungus can remain on some geological tiles, observe fungus yields before and geology bonus after clearing, inspect blue-grey Titanium/Uranium resource layering, and confirm same-build save→quit→reload→advance. ## REND-005 Titanium underlay native-pointer mismatch — Windows evidence, 7 November 2026

The instruction bytes at the static callsite reference `0x78A72C`, but the selector receives `0x78A700` in this Windows callback; do not conflate the two observations or claim the reason for this discrepancy is established.

**Source correction prepared on PR #4:** permit exactly `0x78A700` and `0x78A72C` in the existing early-underlay native pointer guard and log the observed `native_variant` (0 or 1), while retaining the earlier cached tile type and palette readiness checks.
